# docs/reference — 제품 설명 사본

마이크로사이트(www.metadrag.ai · www.lucyware.ai)의 제품소개서를 쓰기 위해 **각 제품 저장소에서
만들어 가져온 문서**를 둔다. 홈페이지 세션은 제품 코드를 열지 않으므로, 제품이 무엇을 하는지는
이 문서로 안다.

| 파일 | 원본 | 사이트 |
|---|---|---|
| `metadrag.md` | `metadrag` 저장소의 `docs/product-overview.md` | www.metadrag.ai |
| `lucyware-ai.md` | `lucyware-ai` 저장소의 `docs/product-overview.md` | www.lucyware.ai |

## 규칙

- **여기서 고치지 않는다.** 이 폴더의 파일은 사본이다. 틀린 것이 보이면 제품 저장소 쪽을 고치고
  다시 복사한다. 사본을 고치면 두 벌이 어긋나고 어느 쪽이 맞는지 아무도 모른다.
- **파일 머리에 작성일과 기준 커밋 해시가 있어야 한다.** 그래야 사본이 어느 시점의 제품을 말하는지
  알고, 오래된 것을 가려낼 수 있다.
- **코드 · DDL · 설정값 · 접속정보 · 고객 이름 · 고객 데이터는 들어오지 않는다.** 프로젝트 사이에는
  결정만 오간다(상위 `CLAUDE.md` 의 「경계」). 제품이 무엇을 하는지를 말로 적은 것만 넘어온다.
- **「계획」 으로 표시된 기능은 사이트에 쓰지 않는다.** 제품 설명은 영업 자리에서 그대로 약속이 된다.
  완성된 것만 소개서에 들어간다.
- 제품 안의 이름과 사이트의 이름이 다르면 문서에 둘을 나란히 적어 둔다. 어느 쪽을 쓸지는 사람이
  정한다 — 한 층에 이름을 둘 달지 않는다.

## 문서를 만드는 요청문

각 제품 저장소의 Claude Code 세션에 아래를 그대로 붙여 넣는다. 첫 줄의 도메인만 바꾼다.

```
마이크로사이트(www.metadrag.ai) 제품소개서를 쓰기 위한 참고 문서를 docs/product-overview.md 로 작성해 줘.
읽는 사람은 이 코드를 모르는 홈페이지 작업 세션이다. 코드 · DDL · 설정값 · 접속정보는 넣지 말고, 제품이 무엇을 하는지만 말로 적어.
차례:
1. 한 줄 정의와 제품이 푸는 문제
2. 구성 — 판(앱) · 모듈 목록과 각각이 하는 일
3. 화면(메뉴) 목록 — 화면마다 사람이 거기서 무엇을 하는지 한 줄
4. 핵심 기능 — 하나마다 「완성 · 진행중 · 계획」 을 표시한다. 계획인 것은 사이트에 쓰지 않는다
5. 데이터 흐름 — 무엇을 읽어 무엇을 만들고 어디에 저장하는지
6. 용어집 — 제품 안에서 쓰는 이름과 뜻. 홈페이지가 쓰는 이름(표준화 · 데이터마트 · 온톨로지 · M³ Dataset · Business Context Object)과 다르면 둘을 나란히 적는다
7. 배치 · 설치 형태 — 컨테이너 구성, 지원 DB, 인증 · 권한, 사내망 설치 가능 여부, 외부 서비스 의존(모델 API 등)
8. 다른 제품과의 연동 지점 — 실제 코드에 있는 것만
9. 화면 캡처 후보 — 어느 화면의 어떤 상태를 찍으면 설명이 되는지
10. 사이트에 쓰면 안 되는 것 — 없는 기능, 고객 이름 · 고객 데이터, 미확정 사항
맨 위에 작성일과 기준 커밋 해시를 적어.
```

만들어진 `docs/product-overview.md` 를 위 표의 이름으로 이 폴더에 복사하고 커밋한다.
